# Taskscope: Fix Student Import False Missing Full Name Validation

## Objective

Fix the student Excel import flow so rows that contain complete student name data are not rejected with the validation error "Full name is required".

The reported issue is that the uploaded Excel file has all required student data, but preview validation still reports a missing full name. The import should correctly recognize either a combined full-name column or split name columns from the provided template.

## Current Findings

The relevant implementation is in:

- `frontend/src/components/popups/ImportStudentPopup.tsx`
- `frontend/src/api/student-api.ts`
- `backend/src/students/students.controller.ts`
- `backend/src/students/students.service.ts`
- `backend/src/students/test/students.service.spec.ts`

The current student import flow already uses:

- `POST /students/import/preview`
- `POST /students/import/confirm`
- `GET /students/import/:sessionId/progress`

The likely root cause is in the field extraction contract between frontend and backend:

- The Excel template generated by `ImportStudentPopup` uses split name columns: `Ma SV`, `Ho dem`, `Ten`, `Gioi tinh`, `Ngay sinh` in display terms, corresponding to Vietnamese UI headers.
- The frontend preview helper can combine `Ho dem` and `Ten` into a display-only `fullName` for local row mapping.
- The frontend still sends the original `rawRows` to `studentApi.previewImportStudents(classId, rawRows)`.
- Backend validation in `StudentsService.extractStudentFields` is authoritative, but it only reads a combined full-name field such as `full_name`, `fullName`, `Ho va ten`, or `Ho ten`.
- Backend validation does not currently combine split name columns like `Ho dem` plus `Ten`.

Because of that mismatch, a row can look complete in the Excel file and in the frontend local parsing, but backend preview still receives no `full_name` and rejects the row.

There is a second risk around exact header matching:

- Header names may include extra spaces, non-breaking spaces, BOM characters, different capitalization, or accented/unaccented Vietnamese variants.
- Current matching is mostly exact string matching plus lowercase/trim comparison.
- This can still fail for visually identical headers that are not byte-identical.

## Problem Statement

Student import validation must not depend on only one exact header spelling for the full name.

The backend preview must accept the template generated by the application itself. If the official template uses split family/middle name and given name columns, then backend validation must combine those fields into `full_name`.

The frontend should also use the same extraction rules for displaying preview/result names so users see consistent row data before and after import.

## Required Behavior

### 1. Accept Combined Full Name Columns

The import preview must continue to accept existing combined-name formats:

- `full_name`
- `fullName`
- `Ho va ten`
- `Ho ten`
- Accented Vietnamese equivalents
- Reasonable variants with extra spaces or different capitalization

When a combined full-name value is present and non-empty, it should be trimmed and used as the imported `full_name`.

### 2. Accept Split Name Columns From The Official Template

The import preview must also accept split-name formats:

- Family/middle name plus given name from the official Vietnamese template
- `Ho dem` plus `Ten`
- `Ho` plus `Ten`
- `last_name` plus `first_name` if already supported by the existing import conventions

When both split fields exist:

```text
full_name = trim(family_or_middle_name) + " " + trim(given_name)
```

If only one split field exists and no combined full-name field exists, validation should still fail with a clear row-level error because the imported full name would be incomplete.

### 3. Normalize Headers Before Matching

Header matching should be tolerant of common spreadsheet formatting differences.

Normalize headers by:

- Trimming leading and trailing whitespace.
- Collapsing repeated internal whitespace.
- Removing BOM and zero-width characters.
- Converting to lowercase.
- Treating non-breaking spaces as normal spaces.
- Supporting both accented and unaccented Vietnamese aliases where practical.

The goal is not to accept arbitrary unknown schemas, but to avoid false errors when the user uses the official template or a visually equivalent header.

### 4. Keep Backend Validation Authoritative

The backend must remain the source of truth for import validation.

Frontend parsing may help with display and local UX, but the backend preview must independently:

- Extract student code.
- Extract full name from combined or split columns.
- Extract date of birth.
- Extract sex.
- Validate email when present.
- Validate duplicates and class scope.
- Create the import session only from normalized backend data.

Do not rely on frontend-only derived `fullName` values for the final import session unless they are explicitly sent as normalized backend input and still validated.

### 5. Align Frontend Display With Backend Extraction

The preview and final result UI should show the same full name that backend validation resolved.

Preferred behavior:

- Backend preview errors include `fullName` when a row has enough name data to resolve it.
- Frontend result mapping uses backend-provided row data when available.
- Frontend local fallback should use the same alias list and split-name logic as backend.

This prevents a confusing case where the UI displays a name in one place but the backend validation says the name is missing.

## Proposed Backend Changes

### Add Header Normalization Helpers

Add small helpers inside `StudentsService` or a nearby import utility:

```ts
private normalizeImportHeader(header: string): string
private findImportValue(row: Record<string, any>, aliases: string[]): any
private buildFullNameFromRow(row: Record<string, any>): string | undefined
```

Recommended matching approach:

- Build a normalized-key map once per row.
- Normalize all aliases with the same helper.
- Use exact normalized-key lookup first.
- Keep current direct lookup behavior if needed for compatibility.

### Update Full Name Extraction

Update `extractStudentFields(row)` so `full_name` is resolved in this order:

1. Combined full-name aliases.
2. Split family/middle-name plus given-name aliases.
3. Undefined when no valid name can be resolved.

Recommended alias groups:

```ts
const combinedName = findValue([
  'full_name',
  'fullName',
  'Ho va ten',
  'Ho ten',
  'Họ và tên',
  'Họ tên',
]);

const familyName = findValue([
  'Ho dem',
  'Họ đệm',
  'Ho',
  'Họ',
  'last_name',
  'lastName',
]);

const givenName = findValue([
  'Ten',
  'Tên',
  'first_name',
  'firstName',
]);
```

If `combinedName` is blank, build `full_name` from `familyName` and `givenName`.

### Return Resolved Full Name In Preview Errors

Extend the preview error shape if needed:

```ts
{
  row: number;
  studentCode?: string;
  fullName?: string;
  reason: string;
}
```

When a row has a resolvable name but another field fails, include `fullName` in the error so the UI report remains useful.

For the specific missing-name case, `fullName` can be empty, but the reason should remain clear.

### Keep Import Session Data Normalized

`session.validItems` should store the normalized `full_name` that backend resolved.

Do not store raw split-name values as the final import name.

## Proposed Frontend Changes

### Reuse The Same Name Aliases In ImportStudentPopup

Update `ImportStudentPopup` local mapping so row-to-name display supports:

- Combined full-name aliases.
- Split family/middle name plus given name.
- Normalized header lookup.
- Extra spaces and visually equivalent headers.

This local parsing is only for display. Backend response should still win when it includes resolved data.

### Verify Template And Parser Are Consistent

The downloaded template must be accepted by backend preview without requiring users to rename columns.

If the template continues to use split columns, backend must support them.

If the product decides to move to a combined full-name column instead, update both:

- Excel template headers and sample rows.
- Backend alias list and tests.

Do not leave the template and backend parser with different contracts.

## Implementation Plan

### Phase 1: Reproduce And Confirm

- Use a row shaped like the current template: student code, family/middle name, given name, sex, and date of birth.
- Call `StudentsService.importPreview`.
- Confirm the current result reports "Full name is required".
- Confirm no database write happens during preview.

### Phase 2: Fix Backend Extraction

- Add normalized header lookup.
- Add combined-name alias support using normalized lookup.
- Add split-name alias support.
- Trim values before validation and session storage.
- Preserve existing student code, date, sex, email, duplicate, and user ID behavior.

### Phase 3: Align Frontend Preview Display

- Update local row-name extraction in `ImportStudentPopup`.
- Prefer backend-provided `fullName` in preview and final reports.
- Keep local fallback only for backward compatibility.

### Phase 4: Regression Tests

Add or update backend tests for `importPreview`:

- Official template row with split family/middle name plus given name is valid.
- Combined full-name row remains valid.
- Unaccented `Ho dem` plus `Ten` row is valid.
- Headers with leading/trailing spaces still match.
- Blank family/middle name or blank given name without a combined full name fails with the missing full name error.
- A valid split-name row stores `full_name` in `session.validItems`.
- Rows failing other fields include the resolved `fullName` in preview errors where possible.

Add or update frontend tests if test infrastructure exists:

- Template-shaped rows display the correct full name in preview errors/results.
- The validation action calls preview and does not call direct bulk creation.

### Phase 5: Manual Verification

Verify from the student class page:

- Download the current student import template.
- Fill all required fields using the split family/middle name and given name columns.
- Upload and click the validation/check action.
- Confirm the row is counted as valid and no "Full name is required" error appears.
- Confirm import can be completed after explicit confirmation.
- Confirm the created student has `full_name` equal to the combined value from the two name columns.

## Acceptance Criteria

- The official downloaded student import template validates successfully when all required fields are filled.
- Rows with split family/middle name and given name no longer fail as missing full name.
- Rows with a combined full-name column still validate successfully.
- Header normalization handles common whitespace and capitalization differences.
- Backend preview remains authoritative and stores normalized `full_name` in the import session.
- Preview/result UI shows consistent full names.
- Existing duplicate, date, sex, email, permission, confirm, progress, account creation, and summary point side effects do not regress.
- Regression tests cover split-name and combined-name imports.

## Out Of Scope

- Redesigning the full student import UI.
- Changing the two-step preview/confirm/progress import flow.
- Changing student schema fields.
- Changing account activation, password reset, lock/unlock, or login behavior.
- Changing academic record import behavior.
- Supporting arbitrary user-defined Excel schemas beyond documented aliases.

## Notes

- This is a parser/validation contract bug, not a missing data issue in the uploaded file.
- The application-generated template and backend import parser must stay in sync.
- Keep code comments and file output in English.
- UI copy may remain Vietnamese to match the existing application.
